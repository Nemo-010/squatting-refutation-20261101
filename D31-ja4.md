Part of the refutation sweep (#1).

**Claim under test.** JA4 is the right fingerprint for this threat because it hashes sorted cipher/extension lists, so ordering randomisation no longer breaks it; do not build policy on JA3 deny-lists because uTLS reproduces Chrome (`research/network-flow-heuristics-proxyjacking.md` §1).

**The corpus answers its own question.** "uTLS reproduces Chrome closely enough that a client either looks exactly like Chrome or looks random each time." The first branch is the bypass: a client that looks exactly like Chrome has Chrome's JA4, and Chrome is what most of the traffic on the Electrosphere already is. A JA4 match on `t13d1516h2_…` is not evidence of anything.

**This is a library fingerprint, not an intent fingerprint.** It tells you which TLS stack built the ClientHello. Xray, sing-box and hysteria all offer uTLS precisely so the answer is "Chrome". Any rule that alerts on a *known proxy* JA4 will either miss the uTLS build or fire on every browser-based automation on the host.

**The random branch is not a signal either.** A per-connection hash change is what an extension-order randomiser looks like. It collides with browsers that permute ClientHello order — which is a smaller set than "every legitimate client", because curl, Go, Java and Python each emit one *stable* JA4 per build.

**REALITY matches the server side, not the client's JA4.** JA4 hashes the ClientHello, which the client's uTLS profile determines; JA4S hashes the ServerHello, which REALITY borrows from the target site. So REALITY makes the *server* match the borrowed site and leaves the client to look like whatever browser it claims. A rule on the pair is defeated by choosing the profile, not by the borrowing.

**Verdict: indistinguishable.** No fingerprint separates the squat from a browser, because the squat's design goal is to produce the browser's fingerprint and it succeeds. Several other issues in this sweep reach the same conclusion for the same reason (D01, D03, D52); this one is not special. What residue exists is an allowlist of expected fingerprints per host — a host-inventory problem, not a flow problem.
